What's inside a resume file

Before you judge an OCR technique, check whether the file gives it anything to read.

Your win today: open any PDF or DOCX and say, with evidence, whether it needs OCR, and what can still go wrong if it doesn't. About 20 minutes.

Three ways a resume holds its words

These three files look identical on screen. Each is the same synthetic resume for "Jordan Sample". A parser gets three very different things.

DOCX

Characters, stored as text in XML

<w:p>
  <w:r>
    <w:t>Jordan Sample</w:t>
  </w:r>
</w:p>

Read the XML. No OCR.

Born-digital PDF

Glyphs drawn at positions on a page

/F4 34.66 Tf
1 0 0 -1 48 85 Tm
<002D> Tj
19.94 0 Td <0052> Tj
21.84 0 Td <0055> Tj
…

Pick font F4, move to a spot, draw glyph 2D (J), step right, draw 52 (o)… Map glyphs to letters, rebuild the order. No OCR.

Image-only PDF

One picture of the page

1 image, 1632 × 2112 pixels
0 fonts
0 characters

Nothing to read. OCR needed.

DOCX. A .docx file is a ZIP archive of XML files, called parts. The body sits in word/document.xml as paragraphs (<w:p>) made of runs (<w:r>) that hold text (<w:t>) (Microsoft Learn). The words are already characters, so there is nothing to recognise. Headers and footers live in their own parts, and text boxes are separate "stories", so a careless parser can still miss text.

Born-digital PDF. A PDF is a list of drawing instructions. The middle card is real: it's the top of our sample PDF, printed by Chrome. Each Tj draws one glyph by its number in the font, and a separate map in the file turns glyph numbers back into Unicode letters for copy-paste (pdfminer.six FAQ). There are no words, lines or columns in there. In pdfminer.six's words, a PDF "is only aware of the characters and their placement" (pdfminer.six). Extractors rebuild words, lines and reading order from positions. Characters you can extract this way are what people call a text layer.

Image-only PDF. A scanned or flattened PDF holds a picture of each page and no characters at all. Text extractors get nothing: pdfplumber's README says it works best on machine-generated PDFs and does no OCR (pdfplumber). Only OCR can turn pixels back into characters. This is the file type where OCR earns its keep, which is why your test set will include it.

A text layer can still fail you

Finding characters isn't the same as having the resume. Three things go wrong, and OCR fixes only one of them.

1 · Wrong order

Two-column resumes put contact details and skills beside the job history. A reader that goes straight across the page merges the two, as you just saw. The fix is layout analysis, which finds the columns before reading them (rung 2 on the compute ladder). OCR won't help, because the characters were never the problem. Alibaba's production resume parser added a layout detector for exactly this: about 20% of its resumes were multi-column (arXiv 2510.09722).

2 · Garbled characters

If the glyph-to-Unicode map is missing or incomplete, the page still looks perfect, but every extractor gets junk. pdfminer.six prints placeholders like (cid:72) (pdfminer.six FAQ). The FAQ's quick test: copy a line from a PDF viewer into a text editor. Gibberish there means gibberish for your parser, so treat the page as a picture and OCR it.

3 · Someone else's OCR

Some scanned PDFs already carry a text layer that an earlier tool added by running OCR. Making scans searchable this way is exactly what OCRmyPDF does. The text is selectable, but it keeps that tool's mistakes. For evaluation this is a trap: if your "scanned" test files still have a text layer, a vendor can score well without doing any OCR. Before you trust a flattened test file, check that it really has zero characters.

The triage

Four questions, in order, for any resume file. They're also on the input triage card.

  1. Is it a DOCX? Read the XML, including headers, footers and text boxes. OCR only embedded images that contain text.
  2. PDF: does the page have a text layer? If not, OCR the page.
  3. Does it copy-paste as real words? If not, treat it as a picture and OCR it.
  4. Is it in reading order? Columns or sidebars need layout analysis. Still no OCR.

A Mac caveat for step 3: Preview's Live Text can select words inside pictures by recognising them on the fly (Apple Support). Selectable text doesn't prove a file has a text layer. The inspector does.

This is question 1 of your evaluation scorecard. Put it to any vendor: "Do you read the text layer when one exists, or OCR every page? And what do you do with DOCX?" A product that OCRs born-digital files pays for compute it doesn't need, and risks recognition errors the text layer would have avoided.

Why this matters at each stage. Tech: it decides what a model is even given. Validation: your test set needs all three file types, or OCR never gets tested. Benchmarking: split every score by file type. Production: route each file to the cheapest rung that can read it.

Check yourself

From memory first. A recruiter asks why their two-column resume came out scrambled when "the PDF has text in it". Answer in two sentences, then compare.

Compare with a model answer

The PDF stores each character with a position on the page, not in reading order, so the parser read straight across both columns and mixed the sidebar into the job history. It needs layout analysis to find the columns first; OCR wouldn't help, because the characters were already right.

1. A candidate uploads resume.docx, typed in Word. What does reading its body text require?

  1. Parse the XML inside the ZIP
  2. Render each page, then run OCR
  3. Show page images to a model
  4. Map glyph numbers to the letters
Right. The body is <w:t> elements in word/document.xml. Read those, plus the header, footer and text-box content. OCR only images embedded in the file.

2. The inspector shows a PDF page with 0 characters and 1 image, though it looks like a normal resume. What's the next step?

  1. Sort its text into column order
  2. Copy the text into an editor
  3. Run OCR on the page image
  4. Unzip it and read the XML
Right. Zero characters plus an image means the page is only pixels, and OCR is the only way back to text (rung 1 or higher on the ladder).

3. A two-column PDF has a clean text layer, yet the parsed profile lists "Python" as an employer. What fixes it?

  1. OCR to reread every character
  2. Layout analysis to restore order
  3. Rendering at a higher resolution
  4. Running spellcheck on the text
Right. The skills sidebar was read across into the job history. Layout analysis finds the columns first, then reads each in turn (rung 2 on the ladder).

4. You "flatten" 50 resumes for the OCR part of your test set, but the inspector still finds a text layer on every page. Why does that matter?

  1. The files would become too large
  2. The page images would lose quality
  3. Text layers slow down every parser
  4. A vendor could skip OCR entirely
Right. A sensible pipeline reads an existing text layer and never runs OCR, so your "OCR" test would only measure text extraction. Flattened test files must show zero characters.

5. A vendor reports 99% accuracy on resumes. Their test set was all born-digital PDFs and DOCX files. What did that number mostly measure?

  1. Their OCR on hard scanned pages
  2. How they cope with photographed pages
  3. Reading text layers, not their OCR
  4. Their speed on a large batch
Right. Every file carried its own characters, so the score mostly reflects extraction and ordering. Ask for results split by file type, including image-only PDFs. That's scorecard question 6, evidence quality.
